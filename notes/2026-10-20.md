## 1. #1321 Restaurant Growth: frame version (re-solve, no count) ✅
Time: 7:00–7:40 (cap was 25, ran 40, partly frame explanation).
Design (own): aggregate to one row per day → SUM over ROWS frame → skip first 6 days with OFFSET + final ORDER BY.

```sql
-- Input grain: one row = one customer visit (customer_id, visited_on)
-- Output grain: one row = one visited_on, from the 7th day on
-- Window needed? yes: SUM of daily totals over a 7-row frame (6 PRECEDING + current)
-- Keep a row when: it is the 7th day or later (full 7-day window)
WITH daily_totals AS (
    SELECT visited_on, SUM(amount) AS daily_total
    FROM Customer
    GROUP BY visited_on
),
seven_day AS (
    SELECT visited_on,
           -- no tie-breaker needed: visited_on is unique after GROUP BY visited_on
           SUM(daily_total) OVER (ORDER BY visited_on
                                  ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS seven_day_total
    FROM daily_totals
)
SELECT visited_on,
       seven_day_total AS amount,
       ROUND(seven_day_total / 7, 2) AS average_amount
FROM seven_day
ORDER BY visited_on
LIMIT 18446744073709551615 OFFSET 6;
```

What went wrong on the way:
- Wanted early rows to be NULL like the LAG version. Frames give **partial windows**, not NULL, and SUM/AVG skip NULLs.
- Final SELECT had no ORDER BY. Then OFFSET was in a CTE and ORDER BY in the final SELECT. **ORDER BY and OFFSET must be in the same SELECT.**
- Added `customer_id` as a tie-breaker. It wasn't grouped, so MySQL silently picked a random value (ONLY_FULL_GROUP_BY off). Postgres/BQ would error. No tie-breaker was needed.
- Names: `dedupe` (it aggregates), `moving_avg` (holds a sum), `amount` reused twice.

## 2. DataLemur Y-on-Y Growth Rate (Wayfair, Postgres): COUNTS ✅
Time: 7:45–8:30. Design (own). Help: EXTRACT syntax; round AFTER ×100.

```sql
-- Input grain: one row = one transaction
-- Output grain: one row = one (year, product_id)
-- Window needed? yes: LAG of yearly spend per product, ordered by year
-- Keep a row when: always (first year per product has NULL prev and NULL rate)
WITH yearly_spend AS (
    SELECT EXTRACT(YEAR FROM transaction_date) AS year,
           product_id,
           SUM(spend) AS curr_year_spend
    FROM user_transactions
    GROUP BY year, product_id
),
with_prev AS (
    SELECT year, product_id, curr_year_spend,
           -- no tie-breaker needed: year is unique per product after GROUP BY
           LAG(curr_year_spend) OVER (PARTITION BY product_id ORDER BY year) AS prev_year_spend
    FROM yearly_spend
)
SELECT year, product_id, curr_year_spend, prev_year_spend,
       ROUND((curr_year_spend - prev_year_spend) / prev_year_spend * 100, 2) AS yoy_rate
FROM with_prev
ORDER BY product_id, year;   -- check the order the problem asks for
```

## Learned today
- **ROWS frame:** `ROWS BETWEEN N-1 PRECEDING AND CURRENT ROW` = slide N rows. It counts rows, not dates. Early rows get partial windows; AVG divides by rows actually seen.
- **Only the outermost ORDER BY guarantees order.** CTE ORDER BY can be ignored; OVER's ORDER BY only orders the calculation.
- Skip rows: MySQL `LIMIT 18446744073709551615 OFFSET n`; BQ also needs LIMIT; Postgres `OFFSET n` alone. Fragile: works on one series only, not per group.
- **Conditional sum:** `SUM(CASE WHEN cond THEN x ELSE 0 END)`; Postgres `SUM(x) FILTER (WHERE cond)`; MySQL/BQ `SUM(IF(cond, x, 0))`.
- Timestamp → date: `CAST(x AS DATE)`; Postgres `x::date`; MySQL/BQ `DATE(x)`.
- Year: `EXTRACT(YEAR FROM d)` everywhere (Postgres returns numeric → `::int`).
- Postgres: int / int = integer division; `ROUND(x, 2)` needs numeric.
