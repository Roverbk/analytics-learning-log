## #1934 Confirmation Rate (Medium) — ACCEPTED, counts

My version (5 CTEs, window-based):

```sql
WITH leftjoin AS (
  SELECT s.user_id, c.time_stamp, c.action
  FROM Signups s
  LEFT JOIN Confirmations c ON s.user_id = c.user_id
),
ranked AS (
  SELECT user_id, action, time_stamp,
         ROW_NUMBER() OVER (PARTITION BY user_id, action ORDER BY time_stamp) AS rnk
  FROM leftjoin
),
confirmations AS (
  SELECT user_id, action, time_stamp, rnk,
         MAX(CASE WHEN action = 'confirmed' THEN rnk ELSE 0 END)
           OVER (PARTITION BY user_id, action) AS confirmed_msgs,
         MAX(CASE WHEN action = 'timeout' THEN rnk ELSE 0 END)
           OVER (PARTITION BY user_id, action) AS timeout_msgs
  FROM ranked
),
dedupe AS (
  SELECT DISTINCT user_id, confirmed_msgs, timeout_msgs FROM confirmations
),
totals AS (
  SELECT user_id, SUM(confirmed_msgs) AS confirmed_msgs,
         SUM(timeout_msgs) AS timeout_msgs
  FROM dedupe GROUP BY user_id
)
SELECT user_id,
       ROUND(IFNULL(confirmed_msgs / (confirmed_msgs + timeout_msgs), 0), 2)
         AS confirmation_rate
FROM totals
ORDER BY confirmation_rate;
```

The query this should have been:

```sql
SELECT s.user_id,
       ROUND(AVG(CASE WHEN c.action = 'confirmed' THEN 1 ELSE 0 END), 2)
         AS confirmation_rate
FROM Signups s
LEFT JOIN Confirmations c ON s.user_id = c.user_id
GROUP BY s.user_id;
```

### What I got right
- Qualified `s.user_id` on the LEFT JOIN — this is what keeps
  zero-confirmation users in the output.
- Added a final ORDER BY without being told.
- `MAX(CASE ...) OVER (PARTITION BY user_id, action)` does work:
  inside a partition `action` is constant, so the CASE is all-true or
  all-false, and MAX(rnk) = count of rows for that action.

### What went wrong
1. **Window + DISTINCT instead of GROUP BY — 4th session running**
   (Odd/Even Oct 20, P4 Oct 21, Odd/Even Oct 22, here Oct 23).
   Output is one row per user → the last step is GROUP BY.
   ROW_NUMBER was never needed; the rank only got used as a counter.
2. **Fragile denominator.** `confirmed/(confirmed + timeout)` assumes
   `action` has exactly two values. Real denominator = all confirmation
   rows for that user = `COUNT(c.user_id)`, or AVG over all rows.
3. **0/0 was accidental correctness.** Zero-confirmation users divide
   0 by 0; MySQL returns NULL and IFNULL caught it. Postgres would
   ERROR. Portable form: `x / NULLIF(y, 0)`.
4. **Four lines: line 4 missing (5th session running).** Line 3's
   "because" was unfinished — finishing it ("which JOB needs the
   window?") would have shown no window was needed and saved 4 CTEs.
   Line 4 should have read: *Keep a row when: every signup survives —
   a user with zero confirmation rows still appears, with rate 0.00.*
5. **Naming.** `rnk` holding ROW_NUMBER (every session since Oct 13);
   `leftjoin` names the operation not the content; `confirmations`
   duplicates the table name `Confirmations` — already on my own
   never-do list.

### Syntax caught during the session
- Unquoted `confirmed` → MySQL reads it as a column → `Unknown column`.
  String literals need quotes.
- `user_id` / `time_stamp` ambiguous after the join (exist in both
  tables) → must qualify with table or alias. On a LEFT JOIN this is a
  correctness issue, not style: `c.user_id` is NULL for users with no
  confirmations, `s.user_id` is not.

## Dialect note
- `a / 0` → MySQL returns NULL; Postgres raises division_by_zero.
  Portable: `a / NULLIF(b, 0)`.
- `AVG(CASE WHEN ... THEN 1 ELSE 0 END)` = rate, works in MySQL, BQ,
  Postgres. BQ shortcut: `COUNTIF(action = 'confirmed') / COUNT(*)`.
  Postgres shortcut: `COUNT(*) FILTER (WHERE action = 'confirmed')`.
